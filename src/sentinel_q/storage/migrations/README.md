# 数据库迁移

表结构的**唯一依据是架构设计文档第五章**。这个目录放的是它的可执行形态。

规则（见架构文档 7.6）：

- 一个编号一个文件，四位编号定宽（`0000_*.sql`、`0001_*.sql`……），**按文件名排序执行**
- **只增不改**：已经执行过的迁移文件永远不再编辑，改动一律新增一个编号
- 契约只允许向后兼容地扩展（加字段、加表），不允许改已有字段的语义
- 真要改语义，走版本号字段，而不是原地改

「只增不改」不是靠自觉：每个文件的 sha256 记在库里的 `schema_migrations`，
下次跑的时候对不上就**拒绝执行**（一个文件都不执行，避免半截状态）。

## 对不上时怎么办：三条出路

1. **把文件改回原样。** 最简单，也最该先想。
2. **新增一个编号，旧文件不动。** 表结构真要改时走这条。
3. **`migrate --accept-drift <版本号> -n "<理由>"`。** 改的确实只有注释、表结构
   一个字都没动时走这条（`2026-09-28` 的 `0002_prompt` 就是：重构把注释里的仓库
   路径从 `core/repo/` 改成了 `storage/`）。

第 3 条**不是把检查关掉**。哈希照旧严格比对，变的只是"对不上之后"：它把
「我看过差异、确认表结构没变」这个**判断本身**记进库——新旧校验和、时间、理由。

需要它是因为引擎手里只有一个哈希：从哈希看，"注释里改了个字"和"DDL 改了、
线上表已经对不上文件"长得一模一样。所以这个判断只有人能下，而人做过的事得留痕。

几条纪律：

- **一次只认一个版本**，理由（`-n`）必填。不能一把梭。
- 先 `--dry-run`：它只读，会把差异和"将要记的那一行"打出来，一个字节都不写。
- 库里存着"当初那版正文"（`applied_sql`）才打得出逐行差异。这个功能之前跑的
  迁移没存过，第一次接受时只能看到两个哈希——**报告会明说"打不出差异"**，
  不会拿现有文件跟自己 diff 装出一个空差异。
- 校验和对得上的老行会在下次 `migrate` 时**自动补上正文**（哈希相等就是
  "文件和当初执行的那一版逐字节相同"的证明）；对不上的不补。

> ⚠️ `0004` 是第一个**带数据前置条件**的迁移：库里若还留着
> `content_type = 'question'` 的行，它会**主动报错停下**并打印该怎么做，
> 而不是让 Postgres 抛一句 "check constraint is violated by some row"。
> 见该文件第 0 步。
>
> 它也是第一个用 `do $$ ... $$` 的：约束名不猜，按**定义**去 `pg_constraint` 里找。

`0000` 单独成一个文件，是为了让 `0001` 保持成 5.4 的**逐字转写**——
以后核对"迁移和文档对不对得上"时可以直接 diff，不用挑出哪几行不是文档里的。

> ⚠️ **这里不会出现爬虫运维表。** 任务断点、URL 清单、限流采样一律是本地文件
> （`runtime/ops/`，见 3.8 与 8.8）——爬虫本地运行，为它建表等于每条 URL 一次
> 网络往返，而运维账本本就不需要跨机器共享。所以库里只有业务数据和提示词。
> 早先计划过的 `0001_ops.sql`（`crawl_keywords` / `crawl_tasks` / `crawl_runs` /
> `crawl_queue`）**已废弃**，不要再加回来。

> ⚠️ 每张表都开了 RLS 且**不建任何 policy**（架构文档 5.7）。原因：Supabase 的
> PostgREST 端点是公开可达的，保护它的只有 RLS。我们自己是表 owner，绕过 RLS。

跑法见 `sentinel_q/storage/__main__.py`：`status` → `migrate --dry-run` → `migrate`。
漂移被拦下时先看 `status` 打出来的逐行差异，再决定走上面三条出路的哪一条。

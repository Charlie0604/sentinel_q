# 数据库迁移

表结构的**唯一依据是架构设计文档第五章**。这个目录放的是它的可执行形态。

规则（见架构文档 7.6）：

- 一个编号一个文件，四位编号定宽（`0000_*.sql`、`0001_*.sql`……），**按文件名排序执行**
- **只增不改**：已经执行过的迁移文件永远不再编辑，改动一律新增一个编号
- 契约只允许向后兼容地扩展（加字段、加表），不允许改已有字段的语义
- 真要改语义，走版本号字段，而不是原地改

「只增不改」不是靠自觉：每个文件的 sha256 记在库里的 `schema_migrations`，
下次跑的时候对不上就**拒绝执行**（一个文件都不执行，避免半截状态）。

已落地：

| 编号 | 内容 | 依据 |
|---|---|---|
| `0000_extensions.sql` | `pg_trgm` 扩展（只开扩展，不建 GIN 索引） | 6.2 |
| `0001_business.sql` | 业务星型模型：`dim_author` / `dim_question` / `dim_event` / `fact_content` / `fact_analysis` / `fact_content_event` / `fact_evidence` | 5.4 |
| `0002_prompt.sql` | `dim_prompt`：提示词的权威副本（不入 git，所以库是唯一能找到它的地方） | 8.9 |

`0000` 单独成一个文件，是为了让 `0001` 保持成 5.4 的**逐字转写**——
以后核对"迁移和文档对不对得上"时可以直接 diff，不用挑出哪几行不是文档里的。

> ⚠️ **这里不会出现爬虫运维表。** 任务断点、URL 清单、限流采样一律是本地文件
> （`runtime/ops/`，见 3.8 与 8.8）——爬虫本地运行，为它建表等于每条 URL 一次
> 网络往返，而运维账本本就不需要跨机器共享。所以库里只有业务数据和提示词。
> 早先计划过的 `0001_ops.sql`（`crawl_keywords` / `crawl_tasks` / `crawl_runs` /
> `crawl_queue`）**已废弃**，不要再加回来。

> ⚠️ 每张表都开了 RLS 且**不建任何 policy**（架构文档 5.7）。原因：Supabase 的
> PostgREST 端点是公开可达的，保护它的只有 RLS。我们自己是表 owner，绕过 RLS。

跑法见 `sentinel_q/storage/__main__.py`：`status` → `migrate --dry-run` → `migrate`。
